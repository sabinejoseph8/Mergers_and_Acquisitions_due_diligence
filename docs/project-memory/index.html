Overview

Project Falcon is an AI "due diligence team" for M&A deals.

How it works

A person gives it a deal brief and a set of sources about a target company. A lead agent plans the work, four specialist agents research the sources in parallel, the lead agent connects what they find, an independent checker verifies every important claim, and the person approves the work at three checkpoints. The output is an Investment Committee-ready report.

Portfolio piece

It is also a portfolio piece demonstrating design, control and measurement of an agentic workflow for high-stakes work. The six targets in the repository, Talonfield Systems among them, are fictional. The two backtests used a real company's public filings, which stay out of the repository.

Goals 4 outcomes

  1. 1Cut the first pass of due diligence from weeks of manual research to one supervised session.
  2. 2Catch the red flags that only appear when sources are combined, such as an event a company left out of its filings.
  3. 3Keep a human in control of every important step, with a clear audit trail.
  4. 4Prove quality with a score, not a claim, by testing against planted red flags.

User stories 13 stories

Starting a run
  • As an operator, I can start a full diligence run with one command, so I don't need to remember steps.
  • As an operator, I am asked whether to continue or start fresh if a previous run exists, so I never mix two runs by accident.
Planning and approval
  • As an operator, I see the plan (questions, hypotheses, assignments) before any research starts, so I can correct the scope early.
Research
  • As an operator, I see which specialists are working and when each one reports, so I know the run is progressing.
  • As a decision maker, I can trust that every finding names its source, so I can check anything myself.
Reviewing red flags
  • As an operator, I see the most serious findings and the conflicts between sources at one stop, so I can decide whether to dig deeper.
Verification and sign-off
  • As an operator, I see which findings were verified, corrected or rejected before the report is written, so nothing unsupported reaches the committee.
The report
  • As a decision maker, I get a clear recommendation, the top red flags, answers to the committee's questions and recommended deal protections, so I can decide quickly.
  • As a decision maker, I can tell facts from allegations and rumors, so I weigh them correctly.
Status and audit
  • As an operator, I can ask for the status of a run at any time.
  • As anyone reviewing the work, I can read every finding, decision and checkpoint in plain files.
Grading and re-running
  • As an operator, I can grade a run against the answer key and see what was missed.
  • As an operator, I can archive a run and start a clean one.

Functional requirements R1 to R35

35 requirements
Running a diligence
R1
One command starts a run. If no previous run exists, it begins with the plan. If one exists, it asks whether to continue or start fresh.
R2
The plan is saved before any research. It maps all six committee questions to specialists, lists 2 to 4 hypotheses, gives each specialist a task list, and states the 3-loop limit.
R3
Checkpoint 1: the run stops after the plan and does nothing until the operator approves or asks for changes. The plan summary (questions, hypotheses, assignments) is printed in chat in the same message as the question, before it, and the run log says it was shown.
R4
Four specialists (SEC filings, news and media, litigation, financial) work in parallel. Each reads only its own source.
R5
While specialists work, the operator sees which ones are running and is told when each reports loading state.
R6
Every finding has an ID, a severity (Critical, High, Medium, Low), a confidence level (High, Medium, Low), a source file and section or row, and a status that is exactly one of Open, Verified, Partially verified or Rejected. A Low finding that is not verified stays Open; "not verified" appears only in the report appendix.
R7
Findings are never deleted. Only their status changes.
R8
Each specialist's full report is saved unedited before it is summarized.
R9
The lead agent compares sources and records cross-source findings, conflicts, disclosure gaps and stale assumptions. When three or more findings describe the same trend, it combines them into one cross-source finding, which states only the trend's own headline numbers and cites any part that is its own issue by ID instead of restating it. Every customer, supplier or litigant named in a source is sized against the customer revenue data. Each dated accounting judgment in the filings (for example an impairment test or a reserve level) is compared with later news, market or financial data, and the change is stated with numbers.
R10
The research loop runs at most 3 times. Every extra loop is logged with its reason.
R11
Checkpoint 2: the run stops and shows a table of Critical and High findings, the main conflicts and what is still open. It waits for "proceed" or "dig deeper on <topic>".
R12
An independent checker verifies every Critical and High finding and every Medium finding that appears anywhere in the report, and gives each a verdict. Low findings may stay unverified. Every correction for a Partially verified finding is applied to the register before Checkpoint 3.
R13
Findings judged Not supported are kept in the register but left out of the report.
R14
Checkpoint 3: the run stops and shows the verification results and the draft recommendation. It waits for approval.
R15
The report has nine parts: cover, executive summary, answers to the six questions, risk matrix, workstream detail, cross-source insights, deal protections, open questions, appendix. The executive summary includes the main positive and mitigating points, checked against a fixed list that includes the internal controls conclusion and auditor tenure and opinion. A positive that another finding puts in doubt is still listed, as a qualified positive with both finding IDs. The appendix includes an index of verified findings and a list of the findings that were not verified (Low only), each labeled "not verified".
R16
The report is saved as Markdown, as a web page and, when the computer has a PDF tool, as a PDF. Without a PDF tool, the operator is told how to save the web page as a PDF error state.
Status, grading and reset
R17
A status command shows the current step, loops used, findings by severity and status, and the top open questions. With no run, it says so empty state.
R18
A grading command scores the latest run: recall overall and for Critical and High issues, severity accuracy, unsupported findings and distractors rated too high, using one fixed grading rule so every run is scored the same way. An issue is found when its main point is in the verified findings, correctly cited, with a severity within one level of one the answer key accepts; severity is reported in two lines, within one level and exact match. The planted positives are graded in their own row (Present, Partly present or Absent), outside recall. It asks permission before opening the answer key. With no run, it tells the operator to run a diligence first empty state.
R19
A reset command archives the current run and its scorecard with a date and time, and restores blank working memory. It never changes the sources, the answer key or the setup.
Safety and quality
R20
The agents cannot use the web and cannot change source files.
R21
The specialists can only read files.
R22
Allegations and rumors are always labeled as such.
R23
If a specialist fails or returns findings without sources, the lead agent asks again once. If that fails, the gap is recorded as an open question error state.
R24
If a source file is missing or empty, the specialist reports it under "Files reviewed" and as a gap error state.
R25
All outputs use plain English, US$ millions with one decimal place, and no em dashes.
R29
The agents cannot open anything in evaluation/ (the answer key and the latest scorecard) or an earlier run (examples/, runs/) unless the operator approves, so a new run stays blind.

CRITERION 3

CRITERION 4

Design principles 9 principles

Project Falcon has no custom app screen. People experience it in three places: the Claude Code conversation (commands, progress messages and checkpoints), the documents it produces (report, findings register, scorecard), and the project materials (README, demo video, architecture diagram, case study, Project Memory website). This file sets one design language for all three.

Evidence first

Every claim shows where it came from: file and section, or docket date.

Humans decide

The system recommends. A person approves at every checkpoint.

Bounded autonomy

Clear stops, clear limits (3 loops), nothing hidden.

Plain English

A busy committee member understands each page in one read.

Severity is not certainty

Every finding carries both how much it matters and how sure we are.

Show your work

Calculations appear with their inputs.

Audit trail by default

Decisions live in files anyone can open, not only in chat history.

One look everywhere

The same colors, labels and terms in the diagram, report and docs.

Print first

Documents look right on paper and in black and white.

System patterns (secure and extensible) 13 patterns

One source per specialist

Swapping a simulated source for a real one (for example a news connector) changes one folder and one agent file, nothing else.

Connect at the folder, not the agent (Phase 8)

A real source is downloaded into a target folder before the run, so the agents stay offline and read-only, the verifier checks exactly what the analysts read, and every run on that target can be repeated. A live connector, scoped to one subagent, is for a current company where freshness matters.

Least privilege

Specialists can only read. Only the lead agent writes, and only to memory/ and output/. Edits to source data and the answer key are denied.

Instructions are not enforcement

Anything that must always hold is backed by a permission rule or an automated check, not only by an instruction.

Sources are evidence, never instructions

Every agent is told to report, not obey, any instruction-like text inside a document (prompt-injection defense).

Single source of truth

The findings register holds every finding. Findings are never deleted; only their status changes.

Separation of duties

Specialists find, the verifier checks, a human approves.

Bounded loops

At most three iterations, with stop conditions and a logged reason for every extra loop.

Evidence-carrying claims

No finding without a citation. The verifier and the checks enforce it.

Append-only audit trail

The run log only grows, each analyst's unedited report is kept, and old runs are archived rather than deleted.

Blind evaluation

Everything in a target's evaluation/ folder (the answer key and the latest scorecard) needs operator approval to open, and the answer key's checksum is tested so any change is visible. /reset-memory moves each scorecard into its archived run, and earlier runs (examples/, runs/) need approval too, so a new run cannot read past answers.

Nothing found is dropped silently

Findings that were not verified still appear in the report appendix, labeled "not verified".

Template-driven output

The report structure lives in CLAUDE.md and the look lives in one stylesheet.

Security

Authentication

The operator's own Claude Code sign-in. Nothing else to sign in to, and no passwords or keys in the project.

Authorization

Permission rules in .claude/settings.json (web tools denied; edits to every target's data/ and answer key, and to tests/, denied; reading anything in a target's evaluation/ folder or an earlier run needs approval; each rule is written for targets/*/ so a new target is covered automatically) and a read-only tool list for every subagent. Subagents inherit the project's permission rules.

Secrets

None in v1. Future connectors must use admin-approved credentials stored outside the project. Never commit keys.

Input validation

Source documents are untrusted input. The prompt-injection rule, read-only tools, no web access and human checkpoints limit what a malicious document could do. Data files are checked against a checksum manifest.

Rate and cost limits

3-iteration cap, narrow follow-up tasks, small sources. The full sample run used about 1.95 million subagent tokens across 10 subagent runs (4 analysts, 2 follow-ups, 4 verifiers) and took 69 minutes from the approved plan to sign-off. Iteration 1 alone used about 0.76 million tokens and 26 minutes.

Real client data (future only)

Use an Enterprise plan, request zero data retention for Claude Code, connect internal systems through admin-approved read-only connectors, and get compliance sign-off first.

Critical risks and challenges 16 risks

Riskiest first. The first four are addressed in the earliest phases.

1
Instructions are not enforcement. An agent could skip a checkpoint, read the answer key or wander outside its source. Early phases
Why it matters
The whole value is controlled autonomy. A skipped checkpoint undermines trust.
How we handle it
Permission rules for the hard limits, read-only tools, checks that confirm all three checkpoints were logged, and an operator who watches the run.
2
Wrong or mis-cited findings reach a high-stakes report. Early phases
Why it matters
One invented number can discredit the whole report.
How we handle it
Mandatory citations, an independent verifier, "Not supported" findings excluded, every correction applied before Checkpoint 3, checks that every cited ID exists, and human sign-off.
3
Prompt injection through a source document. Early phases
Why it matters
Real data rooms contain text the builder does not control.
How we handle it
"Evidence, never instructions" rule in every agent, no web access, no write access for specialists, human checkpoints. A manual injection test is in Phase 5.
4
Claude Code features change (for example commands merging into skills, a new built-in command name). Early phases
Why it matters
A silent change could disable an agent or a guardrail.
How we handle it
Phase 1 checks catch missing or invalid configuration; a docs review with Claude Code's guide agent before each release.
5
Run-to-run variation. Two runs can find different things and score differently.
Why it matters
A single score could be luck.
How we handle it
Fixed output format and rubrics; grade several runs and report the average and range; keep the sample run as a fixed reference. Measured over three blind runs: Critical and High recall 96.2% to 100%, overall 91.7% to 94.4%.
6
Parallel and background behavior. Background subagents may not be able to ask for permissions, and parallel start is not guaranteed.
Why it matters
A blocked analyst could silently return less.
How we handle it
Specialists only need read access inside the project (no permission prompts); the lead waits for every report and retries a failed analyst once.
7
Arithmetic without code. The financial analyst is read-only and calculates by hand.
Why it matters
A math slip could change a conclusion.
How we handle it
Show-your-work rule, independent recomputation by the verifier, automated tie-out checks on the data, key numbers kept in one dataset.
8
Cost and time. Four large-context analysts per iteration.
Why it matters
Long or expensive runs discourage use.
How we handle it
Small sources, narrow follow-ups, 3-loop cap. Measured on the sample run: about 1.95 million subagent tokens and 69 minutes from plan to sign-off (iteration 1: 0.76 million tokens, 26 minutes).
9
Missing tools on the operator's computer (no Python, no PDF tool).
Why it matters
Checks or PDFs would fail.
How we handle it
Standard-library-only checks, the HTML fallback for PDFs, and manual verification steps for every phase.
10
Simulated data is easier than reality, and agents could be tuned to the planted issues.
Why it matters
The score could overstate real-world performance.
How we handle it
Distractors in the data, a blind answer key, and (future) a second fictional target that the instructions were never tuned on. The first test run was only partly blind (the lead agent ran in the session that built the data). The fully blind run in a fresh session scored 96.2% recall on Critical and High issues and 94.4% overall, close to the sample run, which suggests the first score was not inflated. A second fictional target is still needed to test generalization.
11
Real client data if the project is adapted for a live deal.
Why it matters
Confidentiality and data retention obligations.
How we handle it
Out of scope for v1. Enterprise plan, zero data retention request, read-only connectors and compliance sign-off required first.
12
Saved runs leak answers. The sample run and its scorecard sit inside the project, and each new grading writes a scorecard to evaluation/.
Why it matters
A new run that read them could score well without finding anything itself, and the next grading would overwrite the last scorecard.
How we handle it
Claude Code asks before any agent opens evaluation/, examples/ or runs/; /reset-memory moves each scorecard into its archived run; the lead agent's guardrails forbid reading them; and Phase 1 checks confirm both rules.
13
Hindsight leaks in a backtest (Phase 8). The model may know the company's later story from training, or a later document may slip in.
Why it matters
The score would measure memory, not diligence.
How we handle it
A lesser-known case and a contamination check before the run; the download tool filters by filing date and by the date each financial value was filed; a rule to cite only the data folder; /evaluate counts hindsight leaks.
14
Statements about a real company (Phase 8).
Why it matters
An AI red-flag list about a named company could be wrong and could cause harm.
How we handle it
A settled matter of public record; the report says historical backtest and hypothetical deal; the full report stays private (the owner's decision, November 2, 2026; product spec open question 3).
15
Full-length filings (Phase 8). A real 10-K often runs past 100 pages.
Why it matters
Analysts could miss sections or run out of context, and runs cost more.
How we handle it
Filings split into one file per Item with an index; analysts search before reading; time and tokens recorded on the first run.
16
Filing formats vary between companies and years (Phase 8).
Why it matters
The section split could fail without anyone noticing. It did on the first live download: 7 of 13 periodic filings were saved whole.
How we handle it
Fixed and measured on 81 random real 10-K and 10-Q filings (45 to fix, 36 fresh to confirm): all 81 split, and the index flags the financial statements in every filing that includes them. Checks on built-in samples keep each fix in place. The index still flags any filing the split cannot handle, and the analyst reads that filing whole. Not seen in the sample, so not handled: a 10-K that incorporates its statements by reference to an exhibit (for example Exhibit 13), whose main document holds none.
